[[spec-conformance]]
== Spec conformance

The specs here conform to spec-specifications 2.0.0, except retired ones.
The contents table above maps each spec's name to its location.

.Divergences
* spec-cli: the rule on where a tool states its choices (spec-cli#declared-choices) sits in a
  paragraph, not in a list item of its own.
* spec-oci-images names the path of its schemas in this repository, although it is a general
  spec; the schema rule asks it to say where they live.
* spec-version-file (retired) conforms to spec-specifications 1.1.0 only; its name breaks 2.0.0.

[[usage]]
== Usage

.Copying files into a project
* Copy files verbatim, keeping their paths, and copy `LICENSE` along with them.
* Copy from a release tag, and note in your project which tag you copied from. A spec also
  states its own version inside the file; any other file is identified only by that release tag.
* Put project-specific additions in separate files next to the copies, so a later sync overwrites
  the copies without merging.

[[releasing]]
== Releasing

. Choose the next release tag: the semver of this repository (for example `0.6.0`).
. For every spec whose version changes, set its `:spec-version:` and its changelog.
. For every schema of such a spec under `agent/schemas/`, set its `$id` and the `const` of its
  `$schema` to the schema's URL at the new tag, and the `const` of its `$conforms_to` to the new
  spec version.
. Check the schemas (`check-jsonschema --check-metaschema`) and render the specs
  (`asciidoctor -v --failure-level INFO`).
. Update the contents table and the spec conformance section above.
. Commit, tag the commit with the new tag and push both.
